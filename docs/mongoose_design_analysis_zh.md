# Mongoose 设计理念与功能裁剪分析

分析日期：2026-11-24  
分析对象：Cesanta Mongoose 7.24，工作区上游基线 `071cd50e`   
范围：以当前 `upstream/` 的 `README.md`、`mongoose.h`、`mongoose.c` 和 HTTP 示例为依据；这是源码与配置分析，不代表对所有平台进行了运行或性能测试。

## 1. 结论摘要

Mongoose 不是单独的 HTTP Server 程序，而是一个面向嵌入式和桌面平台的 C/C++ 网络库。HTTP/HTTPS 服务器只是它提供的能力之一；同一套连接管理和事件回调机制还支持客户端、WebSocket、MQTT、原始 TCP/UDP 等功能。

设计核心是：**把网络连接、协议处理和应用逻辑放进一个可移植的事件循环，用编译期配置适配不同操作系统、RTOS、TCP/IP 协议栈和硬件驱动。**桌面 POSIX/Windows 项目通常直接使用系统 socket；受限设备可以选择 Mongoose 内置 TCP/IP 栈或接入外部网络栈。

Mongoose 的使用粒度主要有两层：

1. 将 `mongoose.c` 和 `mongoose.h` 加入应用，一起编译；
2. 通过 `mongoose_config.h` 或编译器宏选择平台、网络栈、TLS、文件系统及可选功能。

这种方式减少了依赖管理和跨平台适配工作，但也意味着配置必须和目标平台、链接库、证书及存储布局保持一致。并非每种功能都有独立的开关；未使用功能能否从最终程序中剔除，还取决于条件编译、编译器和链接器的死代码删除能力。

## 2. 设计理念

### 2.1 小而完整的可集成核心

上游将核心实现集中在 `mongoose.c` 和公共接口 `mongoose.h`。应用可以直接把这两个文件纳入自己的构建，而不必先构建一套庞大的库工程。头文件同时提供 API 文档、配置项和示例入口，降低了在不同芯片 SDK 或桌面构建系统中的集成成本。

“两个文件”指核心网络库的主要源文件，并不表示每一种产品形态都只需要两份文件：硬件项目还需要 SDK/HAL、板级配置、驱动、证书或网页资源；使用打包网页时，也需要生成并编译资源文件。

### 2.2 事件驱动、单线程友好

应用创建 `struct mg_mgr`，用 `mg_mgr_poll()` 持续轮询。Mongoose 在连接状态变化、HTTP 消息到达、MQTT 消息到达等时机调用应用注册的事件处理函数。典型 HTTP 流程为：

```text
mg_mgr_init
    └─ mg_http_listen
         └─ 循环调用 mg_mgr_poll
              └─ 收到连接/HTTP 事件
                   └─ 应用回调处理并回复
```

网络 I/O 以异步事件和收发缓冲区为中心；事件回调通常应快速返回。阻塞等待或在回调中做长时间工作，会拖延同一管理器中的其他连接。需要 RTOS 时，可在专用任务中运行轮询循环；并不要求每个客户端连接都创建一个线程。

### 2.3 协议 API 与传输后端分层

HTTP 等应用层 API 使用统一的连接和事件模型；底层则可以接操作系统 socket、BSD socket 兼容栈、Mongoose 自带 TCP/IP 栈或指定 RTOS/SDK 接口。应用可以在尽量不改变协议处理代码的前提下更换平台适配层。

网络栈选择是系统集成决策，不能随意叠加多个互相竞争的 TCP/IP 栈。应按目标工程现有条件选择一种后端，并配套选择对应驱动和 socket 适配方式。

### 2.4 按编译目标配置，而非运行时加载插件

平台和功能主要通过预处理宏选择。`mongoose.h` 根据操作系统、SDK 或 `MG_ARCH` 适配类型和系统接口，`mongoose.c` 再按宏包含相应实现。常见配置来自项目的 `mongoose_config.h` 或编译命令行 `-D...`。

这适合固件构建和需要可预测依赖的产品；不同目标通常要各自维护一份配置和构建参数。不能假定修改某个宏就会自动解决芯片时钟、网卡引脚、DMA 缓冲区、TLS 库链接或链接脚本问题。

## 3. 功能特性

| 类别 | 能力概览 | 典型用途 |
|---|---|---|
| HTTP | HTTP 服务端与客户端、请求/响应解析、REST 回复、目录和单文件服务、分块响应、multipart 上传及流式上传 | 设备网页、REST API、配置门户、文件上传 |
| WebSocket | WebSocket 服务端/客户端和帧发送 | 浏览器实时状态、控制与遥测 |
| MQTT | MQTT 连接端与监听端 API、发布/订阅、登录等接口 | 遥测、消息控制、设备通信 |
| TCP/UDP 与网络服务 | 连接和监听 API、DNS 解析工具、SNTP；可选 Modbus/TCP | 自定义协议、时间同步、工业设备通信 |
| TLS | 无 TLS、内置 TLS，或接入 mbedTLS、OpenSSL、WolfSSL、自定义实现 | HTTPS、加密客户端连接 |
| 文件系统 | POSIX、FATFS、LittleFS 适配，以及只读打包文件系统接口 | 桌面静态文件、SD/Flash 文件、固件内网页资源 |
| TCP/IP 栈与驱动 | 桌面系统 socket、外部 BSD socket 网络栈、内置 TCP/IP 栈和多类芯片/接口驱动 | Windows/Linux、RTOS、裸机 MCU、以太网/Wi-Fi/蜂窝模块 |
| OTA | 按目标平台或自定义实现固件升级相关 API，可配合 HTTP 流式接收、回滚机制 | 设备固件远程更新 |
| 设备仪表板 | 可选的 Dashboard 后端、字段组和实时更新接口 | 设备管理页面、状态展示和远程设置 |
| 公共工具 | 字符串、JSON、编码、哈希/密码学原语、计时器、日志和格式化等辅助 API | 减少小型网络应用的附属依赖 |

功能清单是对公共头文件与上游 README 的归纳。具体可用项会受目标宏、外部库和平台移植状态影响；不能据此推断任意目标平台上的全部功能已经经过实机验证。

## 4. 采用的技术方案

### 4.1 语言与集成方式

- 核心以 C 实现，并兼容 C++ 工程使用。
- 通常把 `mongoose.c` 直接编入最终程序，由 `mongoose.h` 暴露公共 API。
- 以 `mg_mgr` 管理器、`mg_connection` 连接对象、事件枚举和回调连接协议层与应用层。
- 常见字符串接口使用带长度的 `mg_str`，避免 API 一律要求 NUL 结尾字符串。

### 4.2 网络栈后端

- **Windows/桌面系统：**使用系统提供的 socket 接口；Windows 构建会用到 Winsock。
- **外部协议栈：**可接入 lwIP、Zephyr、FreeRTOS+TCP、MDK RL 等，通常依赖目标工程已有的接口和配置。
- **内置 TCP/IP：**为受限设备提供 Mongoose 自带栈和对应硬件驱动，适用于支持的 MCU/网络接口。
- **事件轮询：**在桌面 Linux 上可使用相应的 poll/epoll 后端；其他系统按平台适配。

### 4.3 TLS 后端

`MG_TLS` 选择 TLS 实现：`MG_TLS_NONE`、`MG_TLS_BUILTIN`、`MG_TLS_MBED`、`MG_TLS_OPENSSL`、`MG_TLS_WOLFSSL` 或自定义后端。选择外部库时，除设置宏外还要正确提供头文件、库和链接参数；服务端还必须提供证书和私钥。内置后端可减少外部库依赖，但具体密码套件、资源占用和安全要求应结合目标版本与项目需求核对。

上游公共头文件的通用默认值为 `MG_TLS_NONE`；不同架构分支或示例构建参数可以覆盖它。本项目当前 `Script/build.ps1` 显式选择 `MG_TLS_NONE`，以关闭 TLS。

### 4.4 文件与网页资源

目录服务通过 `mg_http_serve_dir()` 等 API 使用选定的文件系统抽象。桌面目标常用 POSIX 文件接口；MCU 可按实际条件接 FATFS 或 LittleFS。资源也可以预先转换成 C 数据并通过打包文件系统服务，适合无法或不希望提供普通目录的固件。

静态服务、上传功能和可写文件系统有不同的安全与资源含义。尤其是上传、删除和目录列出，应由应用明确配置并限制路径、权限和大小，不应因为示例具备这些能力就默认开放到不可信网络。

## 5. 特性如何裁剪

### 5.1 裁剪原则

优先按顺序处理：

1. 确定目标平台和唯一的网络栈后端；
2. 选择必要的 TLS 和文件系统实现；
3. 只打开应用确实使用的可选功能与硬件驱动；
4. 通过条件编译、编译器优化及链接器死代码删除减少产物；
5. 对每个配置重新构建，并检查功能、链接依赖、固件体积和 RAM，而不是根据宏名估算结果。

不要直接从 `mongoose.c` 手工删协议代码作为第一选择。这会增加维护补丁，且上游升级时容易产生冲突。若某项功能没有独立开关，先确认其依赖关系和符号引用；可用链接器消除未引用代码时，也应实际检查 map 文件和最终产物。

### 5.2 常用配置开关

| 目标 | 配置入口/宏 | 裁剪或选择效果 | 注意事项 |
|---|---|---|---|
| IPv6 | `MG_ENABLE_IPV6=0/1` | 不需要 IPv6 时关闭相关实现 | 默认通常关闭；平台/网络栈组合可能有额外约束 |
| SSI | `MG_ENABLE_SSI=0/1` | 关闭或启用服务器端包含处理 | 默认关闭；HTTP 目录服务本身不是 SSI |
| TLS | `MG_TLS=MG_TLS_NONE` 或选择其他后端 | 完全不需要加密时选择 NONE；否则选择一种实现 | `MG_TLS_NONE` 不提供 HTTPS；TLS 会增加代码、依赖和配置工作 |
| 日志 | `MG_ENABLE_LOG=0/1` | 关闭日志代码或保留日志 | 调试阶段通常保留；关闭会减少诊断信息 |
| 文件系统 | `MG_ENABLE_POSIX_FS`、`MG_ENABLE_FATFS`、`MG_ENABLE_LFS` | 选择目标实际使用的文件系统适配 | 不用磁盘目录时，可考虑打包只读 FS 或应用自管文件访问 |
| 内置网络栈 | `MG_ENABLE_TCPIP` 及目标驱动宏 | 仅在采用 Mongoose 内置栈时启用 | 与 lwIP 等外部栈选择互斥；只启用目标实际使用的驱动 |
| IPv4/事件后端 | `MG_ENABLE_POLL`、`MG_ENABLE_EPOLL`、平台 socket 宏 | 使用系统适配的 I/O 等待机制 | 通常由平台分支和构建环境决定，不建议盲目强设 |
| OTA | `MG_OTA` | 默认 `MG_OTA_NONE`；选目标实现或自定义实现 | 涉及 Flash 布局、写入权限、回滚和签名验证，不只是打开一个宏 |
| Dashboard | `MG_ENABLE_MDASH` | 默认关闭；需要设备 Dashboard 时启用 | 要按公共接口约定集成对应后端与网页资源 |
| 健康监测 | `MG_ENABLE_HEALTH` | 默认关闭，可选开启健康信息能力 | 先确认目标平台支持的指标和采集成本 |
| 自定义平台 | `MG_ARCH`、`mongoose_config.h` | 指定自定义架构和平台钩子 | 需要项目自行实现配置和底层依赖，不能仅把架构号改成 CUSTOM |

以上是头文件中可见的常用选项，并非完整宏目录。各宏的默认值可能受架构分支先行定义的影响；应以实际编译时包含的配置顺序和预处理结果为准。

### 5.3 不能假设所有协议都能单独关掉

当前 `mongoose.h` 并没有一个通用的 `MG_ENABLE_HTTP=0` 开关来整体删除 HTTP 模块；HTTP API 是核心能力的一部分。类似地，宏覆盖范围与依赖关系并不一致。对不使用的协议，编译器/链接器能否删除未引用实现取决于构建参数、函数可达性和最终链接方式。应检查二进制大小和链接 map，而不是以“没有调用某 API”推断其一定不在产物中。

## 6. 对当前工作区的适用建议

当前项目是 Windows 桌面 HTTP Server，本地源码位于 `src/`，构建脚本位于 `Script/build.ps1`。脚本使用 MinGW GCC 和 Winsock；最小化配置关闭 IPv6、SSI、TLS、日志、MD5、OTA、Dashboard、健康监测及未使用的网络栈/文件系统后端。应用只调用静态目录服务，允许目录列表，不提供上传和删除处理。

- 继续使用 Windows socket 后端，不启用 Mongoose 内置 TCP/IP 或 MCU 驱动。
- `MG_ENABLE_IPV6=0`、`MG_ENABLE_SSI=0`、`MG_TLS=MG_TLS_NONE` 符合当前 IPv4、无 TLS、普通静态文件的目标。
- `MG_ENABLE_LOG=0` 有助于进一步精简，但会失去运行日志；需要排查端口占用等问题时可临时打开。
- OTA、设备 Dashboard、MCU 网络驱动和嵌入式文件系统不属于当前桌面示例的必要功能，已关闭。
- 本地应用把网站根目录固定为 `web_root/`，监听 `http://0.0.0.0:8000`，并打开目录列表；上传和删除选项保持关闭。

当前最小配置使用 `-Os`、LTO、函数/数据分节、链接器未用代码删除和符号剥离，已成功编译。LTO 前的最小程序为 113,664 字节；加入 LTO 后为 46,080 字节（45.0 KiB）。旧教程构建为 668,874 字节，但它使用不同应用源码、调试信息和构建选项，因此差值不能视为单独由特性宏带来的节省。Windows 可执行文件仍依赖系统 DLL。程序尚未运行，不对 HTTP 行为、IPv4 绑定或目录列表作运行正确性结论。

后续使用 Clang 23.1.5 的 `-Oz` 编译，x64 普通链接产物为 180,224 字节；x86 普通链接产物为 152,064 字节。Crinkler 3.0b 的当前 COFF 对象读取器只接受 x86，因此不能压缩 x64 目标。使用同一组 x86 Clang 对象链接后，常规 Crinkler 产物为 15,928 字节；加 `/TINYHEADER /TINYIMPORT` 后为 13,241 字节。运行验证中，GCC x64、Clang x64/x86 和常规 Crinkler x86 版本均成功提供首页与目录列表；Tiny Import 进程没有建立监听端口，当前环境下不可用。Crinkler 手册也警告 Tiny Import 可能因未来 Windows DLL 导出表变化而失效。

## 7. 优缺点与边界

**优点**

- 核心集成文件少，便于纳入既有 C/C++ 工程。
- 一个事件模型覆盖多种协议，适合资源受限设备和简单服务器应用。
- 能在桌面系统、RTOS 和裸机项目之间复用较多应用层代码。
- 可选择自带网络栈，也能接入已有协议栈；TLS 和文件系统也有多种后端。
- 静态文件服务、上传、REST、WebSocket、MQTT 和 OTA 等功能可以组合成设备管理应用。

**需要权衡**

- 单事件循环要求回调保持短小；CPU 密集任务或阻塞工作需要交给其他执行上下文。
- 配置宏和目标 SDK 组合较多，跨平台可编译不等于每个驱动和协议组合均已在本项目验证。
- 内置 TCP/IP、TLS、OTA 等功能会带来平台配置、内存布局、安全和升级策略责任。
- 将源文件直接复制到项目意味着项目要自行跟踪上游安全更新和版本差异；`upstream/` 备份本身不会自动同步。
- 上游 README 指明 GPLv2 或商业许可。发布或闭源集成前，应根据实际分发方式核对许可义务和商业许可条件。
